### 2026-11-13 구현 범위

- 음성: 복수 후보와 좁은 기술 용어 규칙으로 확인할 구간을 제안한다. 의심 구간은 자동 전송을 보류하며 사용자가 선택한 구간만 치환한다. 원문·확인 여부는 기록에 남고, 미확인 구간을 인용한 교정은 리포트에서 제외한다. 이 경우 숫자 점수도 표시하지 않는다. 설정에 개인 기술 용어를 등록할 수 있지만 iPhone에서 인식기 편향 기능이 지원된다고 가정하지 않는다.
- 첫 인사: 6개 테마 각각 4개 시작 문장 중 최근 3개와 겹치지 않는 문장을 골라 저장한다. 표시·음성·저장 메시지·대화 맥락이 같은 문장을 사용하며 재개 시 유지한다.
- 학습: 리포트의 어휘·표현을 선택해 `/learn`에서 의미·예문 → 빈칸 → 내 상황으로 바꾸기 → 회상 → 간격 복습을 진행한다. 힌트와 지난 답, 원래 리포트, 예문 듣기를 제공한다. 어느 단계에서나 통화·채팅으로 이어갈 수 있다. 이후 표현의 재등장은 문맥 확인 링크로 기록하며 숙달로 단정하지 않는다.
- 비용·품질: 기존 모델·effort·출력 한도·전체 대화 이력을 유지한다. 별도 음성 API나 학습 콘텐츠 생성 호출은 추가하지 않았다. 선택한 표현과 첫 인사 등 짧은 맥락이 기존 대화 호출에 추가되므로 토큰 비용이 정확히 같다는 보장은 아니다.
- 남은 검증: 실제 iPhone의 원음/전사 비교, 음성 재생·지연과 학습의 장기 효과. 추가 뉘앙스·연어 설명, 친숙한 표현의 단계 건너뛰기, 개인별 복습 간격 최적화는 후속 개선이다. 현재 도움 수준과 간격은 간단한 자기평가 규칙이며 검증된 숙련도 모델이 아니다.

## FB-001 음성 전사와 평가의 정확성

**접수:** 2026-11-13. 사용자가 전날 사용 중 `Frontend engineer`라고 말했는데 `Front and engineer`로 인식되어 Claude에 전달되고, 최종 리포트에서 지적받았다고 보고했다. 기존에 알려 준 사용 환경은 iPhone 13 mini의 Chrome이다.

**확인한 구조:** 브라우저 Web Speech를 `en-US`, `maxAlternatives=1`로 사용하고 첫 후보의 텍스트만 전달한다. 인식 결과의 다른 후보·확신도·사용자 확인 여부를 메시지에 저장하지 않는다. 전송 전 확인·수정 기능은 있으나 기본값은 꺼짐이다. 리포트에는 음성 인식 결과라는 일반 지침만 있고, 어떤 구절이 전사 오류인지 판단할 별도 근거가 없다.

**검토안:**

- [x] 브라우저가 제공하는 복수 인식 후보를 수집하고, 개발 용어 및 사용자가 등록한 표현을 근거로 혼동 후보를 제안한다. 후보 수를 늘리는 것만으로 정확도가 보장되지는 않는다.
- [x] `front and engineer → frontend engineer`처럼 전문 용어로 의심되는 구간을 빠르게 확인·수정할 수 있게 한다. 모든 발화를 매번 확인하도록 강제하지 않고 통화 흐름을 유지하는 방식을 검토한다.
- [x] 인식 원문, 사용자가 확정한 문장, 변경한 구간과 확인 여부를 구분해 보관한다. 문장 전체를 AI가 자연스럽게 고쳐 실제 문법 문제까지 없애는 방식은 피한다.
- [x] 전사 오류로 확인된 부분은 문법·어휘 지적 및 감점 근거에서 제외한다. 미확인 구간은 인식 불확실성을 표시하고, 실제 문법 문제를 무조건 인식 오류로 간주하지 않는다. 원음 없이 발음 문제를 단정하지 않는다.
- [x] 기존 Claude 호출에 필요한 최소한의 전사 정보를 함께 전달하는 방안을 우선 검토한다. 별도 교정 모델 호출의 비용·지연 없이 처리할 수 있는 범위를 확인한다.

**완료 기준:** `frontend engineer`와 `front and engineer` 사례에서 잘못된 학습 피드백을 방지하면서 `He don't understand my question` 같은 실제 문법 문제는 보존한다. 전문 용어가 아닌 일반 문장을 잘못 치환하는 경우도 검증한다. 같은 iPhone에서 실음성으로 인식 정확도와 전송 지연을 전후 비교한다.

**브라우저 제약:** 전문 용어를 인식기에 알려 주는 `SpeechRecognition.phrases`는 Safari iOS에서 지원되지 않는 것으로 문서화되어 있어 iPhone의 핵심 해결책으로 전제하지 않는다. 인식 후보 수는 상한이며, 확신도는 인식기의 추정치일 뿐 실제 발화를 증명하지 않는다. [MDN phrases](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition/phrases), [maxAlternatives](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition/maxAlternatives), [confidence](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognitionAlternative/confidence).

## FB-002 통화 시작의 다양성

**접수:** 2026-11-13. 같은 느낌의 문장으로 매번 통화가 시작되어 다양한 시작 방식을 원한다.

**확인한 구조:** 각 테마에 `openingLine` 한 개가 고정되어 있고, 새 통화에서 그대로 화면에 표시하고 읽는다. 이미 시작한 통화를 재개할 때는 저장된 첫 문장을 유지하며 인사를 반복하지 않는다.

**검토안:**

- [x] 테마별로 인사말뿐 아니라 첫 질문·상황·역할이 다른 시작 문장을 준비한다. 예: 업무는 스탠드업, 코드 리뷰, 동료의 도움 요청 등으로 시작한다.
- [x] 최근 사용한 시작 문장의 반복을 피하고 새 통화마다 선택 결과를 저장한다. 새로고침·통화 재개로 첫 문장이 바뀌지 않게 한다.
- [x] 처음에는 검토된 문장 묶음과 선택 로직으로 다양성을 확보한다. 매번 별도 AI 호출을 추가하지 않고 첫 음성 재생 지연을 유지한다.
- [x] 표시된 인사, 실제 음성, 서버에 저장된 첫 메시지, Claude가 받는 대화 맥락이 같은 선택을 사용하도록 한다. 포트폴리오에 없는 사실을 인사에 만들어 넣지 않는다.

**완료 기준:** 같은 테마의 연속된 새 통화에서 시작 상황과 질문이 달라지고, 같은 통화의 재개에서는 일관성이 유지된다. 기존 첫 음성 재생·마이크 진입 동작과 API 호출 수가 악화되지 않는다.

## FB-003 대화에 이어지는 단어와 어구 학습

**접수:** 2026-11-13. 통화·채팅 이후 별도 공간에서 단어와 어구를 이어 학습하고 싶다. 학습 효과를 조사하고 설계한 뒤 적용하되, 단순 테스트나 반복 학습 도구에 머물지 않기를 원한다.

**추가 피드백:** 같은 날 사용자가 실제 대화에서 활용하는 것을 최종 목표로 삼는 데 동의하면서, 그 전에 표현을 충분히 익히는 중간 과정이 필요하다고 강조했다. 설명을 본 직후 자유롭게 말하도록 요구하는 흐름을 보완한다.

**범위 명확화:** 사용자는 중간 학습에 필요하다면 퀴즈·시험·반복 학습을 포함해도 된다고 명시했다. 다만 학습 도구를 과도하게 확장해 서비스의 주된 목적을 잃지 않기를 원한다. LEO의 중심은 영어 대화·통화와 피드백이며, 별도 학습 공간은 여기서 발견한 부족한 표현을 익혀 다음 대화에 활용하도록 돕는 보조 기능이다.

**목표:** 별도 학습 공간에서 이해·연습·회상의 단계를 거쳐 표현을 익히고, 새로운 상황의 실제 대화에서 스스로 사용할 수 있게 한다. 학습 공간은 표현을 저장하거나 숙련도를 시험하는 용도에 그치지 않고, 아직 모르는 것을 배울 수 있는 과정이어야 한다.

### 기능 범위와 우선순위

- 퀴즈·짧은 시험·반복 연습·간격 복습은 이해를 돕거나 기억을 확인하는 데 필요하면 포함한다. 시험 결과는 다음에 배울 내용과 필요한 도움을 정하는 데 사용한다.
- 학습의 출발점과 활용처를 사용자의 대화·리포트에 연결한다. 학습 기능을 확장할 때에는 다음 대화에 어떤 도움을 주는지와 사용 부담을 함께 검토한다.
- 메인 화면과 주요 이용 흐름은 대화·통화·피드백 중심으로 유지한다. 학습은 선택적으로 이용하며, 학습 완료나 시험 통과를 대화 이용의 조건으로 만들지 않는다.
- 초기에는 위 학습 흐름을 지원하는 필요한 활동부터 구현한다. 문제 수, 시험 점수, 학습 화면 체류 시간 자체를 늘리는 방향으로 기능을 확장하지 않는다.
- 음성 인식과 평가의 신뢰성 등 메인 기능의 품질을 먼저 확보한다. 보조 학습 기능이 대화 응답 품질·속도나 비용 관리를 악화시키지 않도록 범위를 정한다.

**연구와 설계 과제:**

- [x] 간격 학습, 답변 생성, 문맥 속 노출, 피드백에 관한 초기 근거를 검토했다. 아래 연구 표에 제2언어 연구와 일반 기억 연구의 범위를 구분했다. 구체적인 활동과 복습 일정은 설계·검증 대상으로 남긴다.
- [x] 자신의 대화·리포트에서 학습할 표현을 고르고 원래 사용한 상황으로 돌아갈 수 있게 한다. FB-001에서 감지한 미확인 전사 구간은 학습 후보에서 제외한다. 감지하지 못한 인식 오류까지 자동 판별하는 것은 아니다.
- [ ] 의미·뉘앙스·함께 쓰는 표현을 예시로 가르치고, 문장 틀과 단서를 제공하는 연습 → 일부를 바꾸는 연습 → 도움 없이 떠올리는 연습 순으로 중간 학습 과정을 설계한다.
- [ ] 막히면 정답 판정만 하지 않고 작은 단서, 문장 틀, 예시 설명으로 돌아갈 수 있게 한다. 잘 아는 표현은 쉬운 단계를 건너뛰고, 도움이 필요한 표현에는 지원을 늘린다.
- [x] 예문 읽기·브라우저 음성 듣기·쓰기와 자율적인 따라 말하기를 지원한다. 매 활동을 음성 인식이나 AI 채점에 의존하지 않고, 음성 인식 텍스트만으로 발음 점수를 만들지 않는다.
- [x] 다음 통화에 목표 표현과 자연스러운 사용 기회를 위한 지침을 전달한다. 표현 사용을 강제하지 않는다. 학습에서는 단서를 줄이는 단계와 다시 요청하는 힌트를 제공한다.
- [ ] 중간 과정에서 뜻의 이해, 문장 틀 활용, 필요한 단서의 정도, 시간이 지난 뒤의 회상을 구분해 관찰한다. 최종적으로 도움 없이 문맥에 맞게 다시 쓰는지를 확인하고, 인식 실패와 표현 사용 실패를 구분한다.
- [ ] 학습 후보 수와 복습 시점은 사용자 부담 및 실제 사용 결과에 따라 조정한다. 기존 리포트·예문 재사용과 대화 내 활동을 우선 검토하고, 새 AI 호출이 필요한 부분은 비용·대기시간을 별도로 산정한다.

**초기 흐름 제안:** 대화에서 표현 선택 → 예시로 의미와 쓰임 이해 → 문장 틀과 단서로 익히기 → 일부를 바꿔 써 보기 → 도움 없이 떠올리기 → 시간을 두고 다시 꺼내기 → 실제 대화에서 활용 → 피드백과 다음 학습에 반영.

**완료 기준:** 처음 접하는 표현도 예시와 도움을 통해 익힐 수 있고, 막혔을 때 설명·단서로 돌아가 다시 연습할 수 있다. 대화와 학습 공간 사이에서 표현의 출처·맥락·진행 상태가 이어지며, 익힌 표현을 새 상황에서 도움 없이 사용하는 여정을 검증한다. 퀴즈 점수만으로 학습 완료를 처리하거나 모든 연습을 통과해야 통화할 수 있도록 잠그지 않는다.

### 학습 흐름의 구체적인 예

다음은 구현 전 설계 예시다. 대화 후 `run into an issue`를 골랐을 때 바로 자유 대화로 넘어가지 않고 아래 과정을 제공한다. 모든 표현에 동일한 문제 수나 순서를 강제하지 않으며, 도움의 정도와 다음 복습은 사용 결과에 따라 조정한다.

| 과정 | 학습자가 하는 일 | 제공하는 도움 |
| --- | --- | --- |
| 의미와 쓰임 이해 | 원래 대화를 다시 보고, `We ran into an issue during deployment.`가 어떤 상황에서 쓰이는지 이해한다. | ‘문제에 부딪히다’라는 뜻, 현재형 `run`과 과거형 `ran`, 함께 쓰는 말과 짧은 예시를 제공한다. 예문을 읽거나 들어 볼 수 있다. |
| 표현의 틀 익히기 | `We ___ an issue during deployment.`처럼 문장을 완성하고 표현을 한 덩어리로 익힌다. | 처음에는 문장 틀과 선택지·단서를 제공한다. 답을 알려 줄 때에는 왜 그 표현이 맞는지와 완성된 문장을 함께 보여 준다. |
| 일부를 바꿔 보기 | 주어·문제가 생긴 상황을 바꿔 `I ran into an issue while testing the app.`처럼 표현한다. | 나머지 문장은 남겨 두고 바꿀 부분을 표시한다. 익숙해지면 문장 틀을 줄인다. 예문의 상황을 사용자의 실제 경험으로 기록하지 않는다. |
| 도움 없이 꺼내기 | ‘배포 중 문제가 생겼다고 동료에게 알리기’처럼 짧은 상황에 한 문장으로 답한다. | 처음에는 목표 표현을 숨기되, 막히면 뜻·첫 단어·문장 틀·예문 순으로 필요한 도움을 선택할 수 있다. 말하기와 쓰기를 선택할 수 있다. |
| 시간을 두고 다시 익히기 | 다음 학습에서 다른 상황으로 같은 표현을 다시 떠올리고, 이전에 어려웠던 부분을 연습한다. | 기억하지 못하면 설명과 예시로 돌아간다. 같은 문항의 반복 횟수 대신 단서 의존도와 지연 회상을 확인한다. |
| 실제 대화에 연결 | 이후 업무 통화에서 예상치 못한 문제를 설명할 기회를 만난다. | 상황은 제시하되 특정 표현을 반드시 쓰도록 요구하지 않는다. 통화 후 실제 사용을 학습 기록에 연결한다. |

빈칸·선택지·반복도 표현을 익히기 위한 활동으로 사용할 수 있다. 각 활동에는 설명, 적용, 단서를 줄여 가는 목적이 있어야 하며 정답 수를 늘리는 것 자체를 목표로 삼지 않는다. 실제 대화에서 사용할 기회가 없거나 다른 적절한 표현을 쓴 경우는 실패로 처리하지 않는다. 관찰 상태는 예를 들어 ‘뜻을 이해함 → 단서를 보고 사용함 → 도움 없이 떠올림 → 시간을 두고 다시 떠올림 → 다른 상황에서 사용함’으로 구분하되, 한 번 성공한 것만으로 숙달을 단정하지 않는다.

## 관리 방식

추가 피드백은 새 ID로 기록하고, 같은 문제의 재현 사례는 기존 항목에 붙인다. 사용자가 보고한 현상, 코드에서 확인한 사실, 제안 중인 해결책을 구분한다. 구현과 검증이 완료되면 운영 반영 여부와 함께 상태를 갱신한다.
