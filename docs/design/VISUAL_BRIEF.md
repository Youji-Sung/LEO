# 시각 방향 브리프

## 왜 이 작업을 하는가

2026-11-04 UI/UX 세션은 문구, 접근성, 토큰·컴포넌트 체계, 정보 설계를 만들었다. 그러나 **시각 방향(서비스가 어떻게 보이고 어떤 인상을 주는가)은 후보 비교 없이 한 가지로 정해졌고, 운영자가 보기에 서비스에 맞지 않았다.** 그 선택은 이전 브리프가 후보와 레퍼런스를 미리 정해 준 탓이 크다. 이번에는 그렇게 하지 않는다.

이 작업은 두 세션으로 나눈다.

- **1차 세션(이 브리프)**: 시각 방향 시안 3개를 실제 화면으로 만들고, 비교할 수 있게 정리해 push한 뒤 **멈춘다**. 고르지 않는다.
- **2차 세션**: 운영자가 고른 방향을 전 화면에 반영한다. (운영자가 선택한 뒤 별도 프롬프트로 시작한다.)

## 운영자가 확정한 것 (바꾸지 않는다)

| 항목 | 결정 |
|---|---|
| 시안 개수 | 3개. 서로 분명히 다른 방향이어야 한다. 한 방향의 변주 3개가 아니다 |
| 선택권 | 운영자. 1차 세션은 추천은 할 수 있지만 선택하지 않고, 어느 하나를 기본값으로 적용한 채 끝내지 않는다 |
| 다크 모드 | 각 시안은 라이트·다크 둘 다 보여 준다 |
| 외부 의존성 | 시안에 필요하면 폰트·아이콘·라이브러리 추가 가능. 이유만 적는다 |
| 기능 | 추가·제거 없음. 화면 구성·흐름은 시안이 필요로 하면 바꿔도 된다 |
| 테스트 | 1차 세션에서는 기존 테스트를 깨도 된다(시안 단계). 2차 세션에서 통과시킨다 |
| Claude API | 실제 호출 0회. `CLAUDE_MOCK=1` |

## 시각 방향을 정할 때 세션이 자유롭게 하는 것

- 어떤 방향을 탐색할지, 무엇을 참고할지, 어떤 사용자 이해에서 출발할지는 세션이 정한다. 이 문서는 후보, 레퍼런스, 금지 목록을 주지 않는다.
- 이전 세션의 산출물(`PRINCIPLES.md`의 톤과 원칙, `SYSTEM.md`의 토큰, `WRITING.md`)은 **입력이지 제약이 아니다.** 시안이 필요로 하면 원칙과 토큰을 고쳐도 되고, 고치면 무엇을 왜 바꿨는지 적는다. 문구 규칙(`WRITING.md`)은 시각과 무관하므로 그대로 쓰는 것을 전제로 하되, 시안이 문구 톤까지 다르게 제안하고 싶으면 그것도 시안의 일부로 보여 준다.
- 참고 자료를 읽으면 출처를 적는다. 읽지 않은 것을 인용하지 않는다. 이 규칙은 결정을 제한하는 것이 아니라 결정의 근거를 운영자가 확인할 수 있게 하기 위한 것이다.

## 1차 세션의 산출물 (운영자가 비교할 수 있어야 한다)

각 시안마다:

1. **실제로 동작하는 화면.** 목업 이미지가 아니라 코드로 구현된 화면. 어느 화면을 시안에 포함할지는 세션이 정하되, **세 시안이 같은 화면 세트**를 보여 줘야 비교가 된다. 운영자가 서비스를 판단하는 데 필요한 화면이 빠지지 않게 한다.
2. **스크린샷.** 같은 화면 세트를 데스크톱·모바일, 라이트·다크로. `docs/design/directions/<시안 이름>/` 아래.
3. **한 쪽짜리 설명.** 이 방향이 서비스를 어떻게 보이게 하려는 것인지, 왜 이 서비스에 맞는다고 보는지, 어떤 사용자 이해에서 나왔는지, 참고한 것, 이 방향을 택하면 포기하는 것. 운영자가 세 장을 나란히 읽고 고를 수 있는 길이.
4. **전환 방법.** 운영자가 로컬에서 세 시안을 번갈아 볼 수 있는 방법(예: 환경 변수, 쿼리 파라미터, 브랜치). 세션이 정한다.

마지막에 `docs/design/directions/README.md`에 세 시안을 한 표로 비교하고, 세션이 추천이 있으면 추천과 이유를 적는다. 그리고 push하고 멈춘다.

## 다음 작업 (운영자 결정 2026-11-05: 시안을 고르지 않고 전부 유지)

운영자는 하나를 고르는 대신 **기본·서재·무대·콘솔 넷을 모두 사용자가 고를 수 있는 기능**으로 두기로 했다. 선택은 설정 페이지에 있고 `UserSettings.direction`에 저장된다(쿠키로 서버 렌더).

따라서 다음 세션의 일은 "고른 방향 반영"이 아니라 **네 시안을 전 화면에서 같은 완성도로 다듬는 것**이다.

- 각 시안 README 10절의 "CSS만으로 못 한 것"(시안당 7~10개)을 해결한다. 마크업이 필요하면 공통 마크업을 바꾸되 네 시안이 모두 깨지지 않게 한다.
- 비교 세트 밖 화면(채팅 목록, 대화 내용, 포트폴리오, 사용량, 회원가입, 다이얼로그·토스트, 설정)을 네 시안으로 모두 촬영·점검한다.
- 접근성(axe 0, 대비 테스트), 반응형, reduced-motion, 테스트 통과를 네 시안 모두에 대해 이전 세션과 같은 수준으로 맞춘다. 대비 테스트는 시안별 토큰도 고정한다.
- 운영자가 외부 테스트에서 받은 피드백(아래)을 반영한다. 어떻게 고칠지는 세션이 정하고 근거를 적는다.

외부 테스트 피드백(2026-11-05, 운영자가 받은 것. 확정 지시가 아니라 관찰이다)
1. 통화에서 상대의 첫 인사말이 대화 내용·메시지 수에 빠진다. 통화 중에는 보이는데 끝난 뒤에는 없다. (1차 UI 세션이 "서버 저장 안 함"으로 정했고, Claude API는 첫 메시지가 user여야 하는 제약이 있다)
2. 빈 채팅의 "영어로 첫 메시지를 보내 보세요" 아래 "Hi! Can I tell you about my week?"가 예시인지 구분되지 않는다.
3. 메시지가 없는 대화가 기록 목록에 "주고받은 말 없음 / 진행 중"으로 남는다(홈에서는 이미 숨김).
4. 마이크가 없는 브라우저에서 "마이크 권한이 꺼져 있어요"가 오류색으로 뜨고 그 아래 "글로 대화해요" 안내가 같이 나온다. 글로 대화하는 것이 정상인데 오류처럼 보인다.
5. 통화에서 실패한 말은 사라지고 다시 보내기가 없다(채팅에는 있다).
6. 리포트 문법 교정이 가끔 사소하거나 중복된다(프롬프트에 규칙을 넣었지만 모델 출력이라 보장되지 않는다).
