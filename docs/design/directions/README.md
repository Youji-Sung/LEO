# 시각 방향 시안 3개 (1차 세션, 2026-11-04)

세 시안을 같은 화면 세트로 만들어 비교한다. **어느 시안도 적용되어 있지 않다**(쿠키가 없으면 현행 화면). 운영자가 맨 아래 "선택" 칸을 채워 push 하면 2차 세션이 그 방향을 전 화면에 반영한다.

문서 순서: `00-understanding.md`(서비스·사용자 이해) → `01-exploration.md`(후보 8개, 선정 이유, 출처) → `02-build-rules.md`(세 시안 공통 규칙과 뼈대) → 시안별 `study/`, `stage/`, `console/`(한 쪽 설명 `README.md` + 스크린샷 `shots/`).

## 로컬에서 보는 방법

1. 서버를 띄운다: `npm run dev` (모의 모드로 보려면 `.env` 에 `CLAUDE_MOCK=1`).
2. **설정 페이지 → 화면 → 디자인 시안**에서 기본(현행)·서재·무대·콘솔 중 고른다. 고르면 바로 바뀐다. 또는 주소에 쿼리를 붙인다. 쿠키(`leo_direction`, 30일)로 저장되므로 그 뒤로는 모든 화면이 그 시안으로 보인다.
   - 서재: `http://localhost:3000/?direction=study`
   - 무대: `http://localhost:3000/?direction=stage`
   - 콘솔: `http://localhost:3000/?direction=console`
   - 현행으로 되돌리기: `http://localhost:3000/?direction=off`
3. 다크 모드는 설정 페이지의 "테마 모드" 또는 OS 설정으로 바꾼다. 세 시안 모두 라이트·다크 팔레트를 따로 가진다.
4. 기본값을 고정하려면 `.env` 에 `LEO_DIRECTION=study|stage|console` (쿠키가 우선).
5. 시안 폰트는 Google Fonts 에서 받으므로 로컬에서 볼 때 인터넷이 필요하다(현행 Pretendard 도 jsDelivr).

스크린샷만 보려면 `docs/design/directions/<시안>/shots/` 에 9개 상태 × 1280/390 × 라이트/다크 = 48장이 있다(`index.md` 에 목록, 전체 페이지 캡처라 고정 요소는 문서 중간에 찍힌다). 다시 찍으려면 `npx tsx scripts/screenshots.ts --direction <시안> --axe`.

## 구현 범위와 한계

- 세 시안은 각각 `src/app/directions/<시안>.css` 한 파일이다(900~1,070줄). 마크업·문구·흐름·기능은 공통이고, 2차 세션이 고른 시안의 CSS 를 토큰(`src/design/tokens.ts`)과 `globals.css` 로 흡수한 뒤 나머지 CSS 파일과 전환 장치를 걷어낸다.
- 비교 세트 밖 화면(채팅 목록, 대화 내용, 포트폴리오, 사용량, 회원가입, 다이얼로그·토스트)도 같은 CSS 가 입히지만 스크린샷으로 확인하지 않았다(미확인). 2차 세션이 전 화면을 다듬는다.
- CSS 만으로 못 한 것(마크업이 필요한 것)은 각 시안 README 10절에 있다. 셋 다 공통으로 주소창 `theme-color`(`layout.tsx` 고정값)를 시안 캔버스색으로 바꿔야 한다.
- 접근성 하한(텍스트 4.5:1, UI 3:1, 타깃 44/56px, reduced-motion)은 세 시안 모두 지켰다. 수치는 각 README 9절, axe 결과는 각 `shots/axe.md`.
- 현행 테스트: 쿠키가 없으면 현행 화면이라 `npm run check` 와 E2E 는 그대로 통과한다(`docs/design/directions/` 커밋 로그 참고).

## 세션의 추천

**서재(study)를 추천한다. 2순위는 무대(stage).**

- 운영자가 "서비스에 맞지 않는다"고 한 현행의 문제를 `00-understanding.md` 3절에서 "익명의 SaaS 관리 화면, 영어와 한국어가 같은 옷, 통화가 채팅처럼, 리포트가 표처럼"으로 가설했다. 서재는 이 넷을 가장 직접적으로 뒤집는다 — 카드·파랑·알약이 사라지고, 영어만 세리프로 다른 목소리를 얻고, 리포트가 장(章)과 교정 원고로 읽힌다.
- 사용자는 시험 앞의 성인이다. 10분 통화와 리포트 읽기(취약한 순간)에서 가장 덜 해로운 선택은 자극을 빼는 쪽이다. 무대의 기세는 시작할 때 좋지만 통화 내내·리포트 내내 유지되고, 콘솔의 정확함은 피드백을 코드 리뷰로 만들어 온기를 문구에만 맡긴다.
- 서재의 약점(활기 없음)은 2차에서 통화 화면에 무대의 "어두운 무대" 아이디어(라이트에서도 통화만 어둡게)를 빌려 보완할 수 있고, 외부 의존성(세리프 2종)은 콘솔과 같은 수준이다.
- 무대를 고를 이유: 브랜드가 분명히 필요하거나, 서재가 "밋밋하다"고 느껴지면. 콘솔을 고를 이유: 두 사용자가 "도구처럼 쓰는" 느낌을 더 원하고 리포트의 diff 표현이 마음에 들면 — 다만 현행도 "개발자 도구 감성"이었다는 점을 생각하면 같은 축을 더 밀어붙이는 선택이다.
