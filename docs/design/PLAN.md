# UI/UX 개선 계획

한 번의 클라우드 세션이 이 문서를 0단계부터 8단계까지 끝까지 수행한다. 각 단계의 완료 조건을 실제로 확인한 뒤에만 닫고, 결과를 `docs/design/PROGRESS.md`에 적는다. 전제·제약은 `docs/design/BRIEF.md`.

공통 규칙
- 조사 없이 만들지 않는다. 0·1단계를 건너뛰고 화면부터 고치지 않는다.
- 모든 결정은 `docs/design/DECISIONS.md`에 "결정 · 근거 · 기각한 대안 · 출처" 형식으로 남긴다. 출처는 URL 또는 문서명. 읽지 않은 것을 인용하지 않는다.
- 단계마다 `npm run check`와 `npm run test:e2e`를 통과시키고 커밋한다. 커밋 메시지는 `design N: 요약`.
- 독립적인 작업(예: 컴포넌트 구현과 라이팅 개정, 화면별 재설계)은 서브에이전트로 병렬화한다. 원칙·토큰·용어집은 메인 세션이 먼저 확정하고 나서 병렬화한다. 그래야 결과가 일관된다.
- 스크린샷은 `scripts/screenshots.ts`(0단계에서 만든다)로 찍는다. 손으로 찍지 않는다.

## 0단계. 현황 조사와 도구

- 스크린샷 스크립트: Playwright로 E2E 서버(모의 모드, 가짜 VoiceAdapter)를 띄워 **모든 화면·주요 상태**(로그인, 회원가입, 홈, 채팅 빈 상태/대화 중/힌트, 통화 설정, 통화 중, 통화 종료 중, 리포트, 리포트 오류, 기록, 포트폴리오 빈 상태/목록, 사용량, 설정, API 키 없음 배너)를 1280px·390px, 라이트·다크로 찍는 `scripts/screenshots.ts`. 출력은 `docs/design/screenshots/{before|after}/`.
- before 스크린샷 전부 촬영.
- 휴리스틱 평가: Nielsen 10원칙으로 화면마다 문제를 적는다(심각도 1~4). `docs/design/AUDIT.md`.
- 접근성 자동 점검: `@axe-core/playwright`로 전 화면 검사, 위반 목록을 AUDIT에 붙인다. 대비는 실제 값으로 적는다.
- UI 문자열 전수 인벤토리: `src/` 안의 모든 사용자 노출 문구(버튼, 레이블, 오류, 빈 상태, 안내, 리포트 섹션 제목, 테마 이름)를 파일·위치와 함께 표로 뽑는다. `docs/design/STRINGS.md`. 전수 확인이며 표본이 아니다. 몇 개 중 몇 개를 확인했는지 적는다.

완료 조건: before 스크린샷이 화면·상태별로 모두 있다. AUDIT에 화면별 문제 목록과 axe 결과가 있다. STRINGS에 전체 문자열이 있고 총 개수가 적혀 있다.

## 1단계. 조사와 원칙

- 외부 가이드라인 읽기: BRIEF의 목록을 실제로 읽고(WebFetch/WebSearch), 이 프로젝트에 적용할 조항을 발췌해 `docs/design/RESEARCH.md`에 출처와 함께 정리한다. 접근 실패는 "확인 못 함"으로 적는다.
- 레퍼런스 분석: BRIEF의 제품들을 검색해 통화 화면, 피드백 화면, 온보딩, 문구 톤을 본다. 각 제품에서 "가져올 것 / 가져오지 않을 것 / 이유"를 적는다.
- 사용자·상황 분석: BRIEF의 출발점을 바탕으로 핵심 순간 3개(통화 중, 리포트 읽기, 채팅)의 사용자 상태(인지 부하, 감정, 손·눈의 자유도)를 적는다.
- 톤 결정: 후보 3개를 사용자·상황·레퍼런스에 비추어 비교하고 하나(또는 혼합)를 고른다. voice & tone 차트(상황별: 시작할 때, 통화 중, 실수를 짚을 때, 칭찬할 때, 오류가 났을 때, 비용·한도 안내)를 만든다.
- 디자인 원칙 3~5개: 각 원칙에 "이 원칙 때문에 하지 않는 것"을 붙인다.
- 산출물: `docs/design/PRINCIPLES.md`(톤, voice & tone 차트, 원칙), `RESEARCH.md`.

완료 조건: PRINCIPLES에 톤 결정과 기각 이유, 차트, 원칙이 있다. RESEARCH에 출처 URL이 있는 발췌가 가이드라인별로 있다. 접근 실패한 출처는 명시되어 있다.

## 2단계. UX 라이팅 가이드와 문구 개정

- `docs/design/WRITING.md`: 한국어 UI 문구 규칙. 최소 포함: 경어 체계(해요체/합쇼체 중 선택과 이유), 버튼은 동사로 끝나는지 명사형인지, 문장 길이, 영어 혼용 규칙(테마 이름·영어 예문·고유명사), 숫자·시간 표기, 오류 메시지 구조(무슨 일이 / 왜 / 어떻게 하면 되는지, 비난하지 않기), 빈 상태 구조(상황 설명 + 다음 행동), 로딩·진행 문구, 확인 대화(파괴적 행동은 버튼에 행동 이름), 칭찬과 교정의 균형(리포트), 금지 표현 목록.
- 용어집: 같은 개념에 하나의 단어. 예: 전화 영어/통화/콜, 리포트/보고서/피드백, 교정/수정/고치기, 상대/파트너/AI, 테마/주제/시나리오. 선택과 이유.
- STRINGS의 모든 문구를 규칙에 맞게 개정한 표(원문 → 개정 → 이유). 바꾸지 않은 문구도 "유지, 이유"로 적는다.
- 코드에 반영. 문구는 가능하면 한 곳(`src/content/` 또는 유사)에 모아 두고 컴포넌트는 참조만 하게 한다.
- 리포트의 Claude 출력 문구(요약·코멘트·설명)는 시스템 프롬프트가 만든다. WRITING의 톤이 프롬프트의 "리포트 문체 지시"에도 반영되도록 `prompts/themes.ts`의 해당 부분을 함께 손본다. 단, 모의 응답으로만 확인하고 실제 호출은 하지 않는다.

완료 조건: WRITING과 용어집이 있다. STRINGS 표의 모든 행에 개정안 또는 유지 사유가 있다. 코드의 문구가 표와 일치한다(grep으로 확인한 결과를 PROGRESS에 적는다). 테스트 통과.

## 3단계. 디자인 시스템(토큰과 컴포넌트)

- 토큰: 색(라이트·다크 각각, 역할 기반 이름: surface/text/accent/positive/caution/negative 등, 모든 텍스트-배경 조합의 대비값 표), 타이포 스케일(한국어 본문 기준 줄 간격·자간, 영어 예문용 스타일), 간격 스케일, 라운드, 그림자/고도, 모션(지속시간·이징, reduced-motion 대체), 브레이크포인트. `docs/design/SYSTEM.md`에 표와 근거.
- 폰트 결정: 한국어·영어 혼용 가독성, 로딩 비용, 라이선스를 비교해 고른다. 웹 폰트를 쓰면 서브셋·프리로드·`font-display`를 설정하고 CLS를 확인한다.
- 아이콘 결정: 세트 선택 이유, 사용 규칙(레이블 없이 아이콘만 쓰는 경우의 `aria-label`).
- 컴포넌트: Button(variants, sizes, loading, icon), TextField/TextArea/Select, Card, Badge/Tag, StatusMessage(info/success/warning/error, `role` 규칙), Dialog(포커스 트랩, Esc), Tabs/Segmented control, EmptyState, Skeleton/Spinner, ProgressRing/Timer, ScoreGauge(리포트 점수), DiffText(원문/교정문 대비), Toast. 각 컴포넌트에 상태(hover/focus/active/disabled/loading)와 접근성 요구사항.
- 구현: `src/components/ui/`. 기존 전역 CSS는 토큰 기반으로 재작성하거나 새 체계로 대체. 결정과 이유 기록.
- 테마 전환: 시스템 기본 + 설정 페이지 수동 전환(저장은 기존 `UserSettings`에 필드 추가가 필요하면 마이그레이션 포함). 전환 시 깜빡임(FOUC) 방지 방법과 확인 결과.

완료 조건: SYSTEM에 토큰 표와 대비값이 있고 AA 미달 조합이 없다. 컴포넌트가 모두 구현되어 있고 각각 단위 테스트(렌더·접근성 속성)가 있다. 다크 모드가 전 화면에 적용된다. 테스트 통과.

## 4단계. 화면별 재설계

우선순위 순서로 진행한다. 화면마다 `docs/design/SCREENS.md`에 "문제(AUDIT 참조) → 결정 → 근거 → 대안 → after 스크린샷 경로"를 적는다.

1. **통화 중 화면** (핵심). 긴장 상태에서 한눈에: 남은 시간, 지금 누가 말하는지, 내 말이 제대로 인식되는지, 끊기. 큰 터치 타깃, 상태의 시각·문자 동시 표시, 끼어들기 안내, 연장 버튼의 타이밍과 위치, 종료 중 안내. 모바일 우선.
2. **리포트**. 피드백을 받는 순간의 정서를 고려한 정보 순서(요약·격려 → 점수 → 교정). 점수 시각화, 원문/교정문 대비의 읽기 쉬움, 긴 리포트의 탐색(목차/앵커), 다음 과제의 행동 유도.
3. **통화 설정**. 테마 선택을 카드로, 각 테마가 어떤 상황인지 한 줄 설명, 시간·포트폴리오 선택, 마이크 확인의 안심감.
4. **채팅**. 스트리밍 표시, 힌트의 시각적 위계(답변을 방해하지 않게), 입력창, 테마 전환, 리포트 생성 진입.
5. **홈**. 다음 행동이 명확한 대시보드(바로 통화 시작, 최근 리포트, 연속 기록 등 기존 데이터로 만들 수 있는 것만).
6. **기록, 포트폴리오, 사용량, 설정, 로그인/회원가입**. 일관성과 빈 상태·오류 상태 중심.
7. **전역**: 헤더/내비게이션(모바일 패턴 결정), API 키 없음·모의 모드 배너, 페이지 전환.

각 화면 작업 후 해당 E2E를 돌리고 셀렉터를 고친다. 기능 흐름은 바꾸지 않되, 바꾸는 편이 낫다고 판단하면 근거를 적고 테스트도 함께 바꾼다.

완료 조건: SCREENS에 모든 화면 항목이 있다. after 스크린샷이 before와 같은 구성으로 모두 있다. E2E 18개 이상 통과.

## 5단계. 상태와 마이크로 인터랙션

- 빈 상태, 로딩(스켈레톤 vs 스피너 결정과 근거), 오류(네트워크·API 키 없음·refusal·턴 상한·스키마 실패), 성공 피드백, 파괴적 행동 확인(포트폴리오 삭제 등) — WRITING 규칙과 컴포넌트로 통일.
- 모션: 통화 중 말하는 상태 표시, 스트리밍 텍스트, 페이지 전환, 토스트. 모두 `prefers-reduced-motion`에서 대체 동작.
- 포커스 관리: 페이지 이동·대화상자·오류 발생 시 포커스가 어디로 가는지 정의하고 구현.

완료 조건: 상태 목록 표(화면 × 상태)에 전부 "구현·스크린샷·테스트"가 채워져 있다. reduced-motion 모드 스크린샷이 있다.

## 6단계. 접근성·반응형·성능 검증

- axe 전 화면 재검사: 위반 0건이거나 남은 항목마다 사유.
- 키보드만으로 3개 핵심 흐름(로그인→채팅→리포트, 로그인→통화→리포트, 포트폴리오 등록→면접) 완료 — E2E로 작성.
- 대비 전수: 토큰 조합 표의 값을 코드에서 계산해 테스트로 고정(`tests/unit/contrast.test.ts`).
- 반응형: 360/390/768/1280 스크린샷 비교, 가로 스크롤 0.
- 성능: 빌드 후 첫 로드의 폰트·CSS 크기, CLS 확인(Playwright로 layout shift 측정 또는 Lighthouse). 수치를 적는다.
- 화면 확대 200%에서 레이아웃 깨짐 없음.

완료 조건: 위 항목마다 수치 또는 통과 결과가 PROGRESS에 있다.

## 7단계. 리뷰 패스

- 서브에이전트 2개에게 각각 (a) after 스크린샷 전체 + PRINCIPLES/WRITING만 주고 "원칙·문구 규칙 위반과 일관성 문제"를 찾게 하고, (b) 코드만 주고 "정확성 버그·접근성 결함"을 찾게 한다. 결론을 주지 않는다.
- 확인된 것만 고치고, 고치지 않은 것은 이유와 함께 남긴다.

완료 조건: 리뷰 결과와 조치가 PROGRESS에 있다. 테스트 통과.

## 8단계. 마무리

- `docs/design/README.md`: 문서 지도(무엇을 어디서 보는지), before/after 대표 화면 비교, 결정 요약.
- 프로젝트 README의 기술 스택·스크립트 갱신(스크린샷 스크립트, 테마 전환).
- 브랜치 push.
- 마지막 메시지: 바뀐 것, 톤·원칙 요약과 근거, 검증 수치, 미확인 항목, 운영자가 봐야 할 것(실제 브라우저에서의 다크 모드·모션·음성 화면).
